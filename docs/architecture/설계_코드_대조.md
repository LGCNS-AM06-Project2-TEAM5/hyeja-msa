# MSA 설계서와 실제 코드 대조 결과

대조 대상: [MSA 아키텍처 설계서](HYEJA_MSA_Architecture_Design.md), 시스템·서비스 구성도, 요구사항 명세서, ERD·테이블 명세서 ↔ [hyeja-backend](https://github.com/LGCNS-AM06-Project2-TEAM5/hyeja-backend) 코드

## 1. 설계서와 코드가 일치하는 것

| 항목 | 설계서 | 코드 확인 결과 |
|---|---|---|
| 외부 API 수 | 29개 | 컨트롤러 기준 29개 (`/api/health` 포함) |
| 테이블 | 9개 | member, profile, region, policy, policy_region, card_news, favorite, notification, term |
| 이메일 찾기 | 구현 여부 확인 필요 | `GET /api/members/find-email` 구현됨 (닉네임 + 생년월일) |
| 비밀번호 재설정 | 구현 여부 확인 필요 | **구현 안 됨.** 1차 수행계획서의 제외 범위. 시스템 구성도의 "비밀번호 재설정 메일"은 신규 기능 |
| 추천 API 경로 | `/api/recommendations`는 확인 필요 | 실제 경로는 **`GET /api/policies/search`**. 프런트도 이 경로를 사용 → 경로 유지, Gateway에서 recommendation으로 보냄 |
| 검색어 길이 | 최대 200자 확인 | 요구사항 명세서와 같음 |
| AI 사용 위치 | 정책 분석·카드뉴스 → Policy, 검색 의도·판정 이유 → Recommendation | `OpenAiPolicyAnalyzer`(수집), `OpenAiPolicySearchAnalyzer`(검색)로 이미 나뉘어 있음 |
| 서비스 사이 FK | 제거 | favorite·notification → member·policy, profile → region FK가 실제로 있음 → 값만 저장으로 변경 |

## 2. 설계서에 빠진 서비스 간 호출 (코드에는 있음)

| # | 호출 | 코드 근거 | 영향 | 제안 |
|---|---|---|---|---|
| 1 | **policy → user** (내 조건) | `PolicyService` 200·249행, `CardNewsService` 60행이 `ProfileService.getActiveProfile` 사용 | `/api/policies/housing/me`, 정책 상세(로그인), 회원 카드뉴스가 내 조건으로 필터·판정 | Feign F6 추가 |
| 2 | **user → policy** (지역) | `MemberService` 66행, `ProfileService` 49행이 `RegionRepository` 사용 | 가입·내 조건 저장 시 거주지 코드 검증, 응답의 시군구 이름 | user_db에 지역 CSV(269건) 복사본, F7 없음 — **#1 확정** |
| 3 | **정책 상세의 자격 판정** | `PolicyService` 252행이 `PolicyEligibilityEvaluator` 사용 | 검색(recommendation)과 상세(policy)가 같은 판정 로직을 씀 | 판정 코드를 policy·recommendation이 같이 씀, F8 없음 — **#1 확정** |
| 4 | engagement → user (회원 확인) | `FavoriteService` 32·56행 `memberService.getActiveMember` | 관심 등록·목록 전 회원 확인 | Gateway가 토큰과 블랙리스트를 확인하므로 호출 없이 생략 가능 |

## 3. 데이터 일관성 위험 (설계서 4장과 같은 결론, 코드로 확인)

| 위험 | 코드 근거 | 대응 |
|---|---|---|
| 회원 탈퇴가 여러 DB에 걸침 | `MemberService.withdraw`가 한 트랜잭션에서 notification·favorite 삭제 → profile·member 소프트 삭제 | `member-withdrawn` 이벤트로 engagement가 정리 (최종 일관성). 실패 시 재시도·DLT. Saga 보상은 선택 |
| 관심 목록 키워드 검색 | `FavoriteRepository` 109·121행이 `policy.policyName`, `policy.supportContent`를 LIKE 검색 | `policy-updated`로 받은 정책 스냅샷에서 같은 조건으로 검색 |
| D-7 알림 대상 | `NotificationGenerationService`가 favorite·member·policy를 함께 조회(삭제·비활성 제외) | 스냅샷의 `activeYn`·`deleted`·`applyEndDate`와 탈퇴 이벤트로 판단 |
| 하트 값 | 목록·상세·카드뉴스·검색이 `FavoriteRepository`를 직접 조회 | F3·F4 일괄 조회, 실패 시 하트 없이 응답 |
| 잘못된 토큰 처리 | 정책 상세는 비로그인 허용이지만 잘못된 토큰이면 오류 (`PolicyController` 244행) | Gateway가 같은 규칙을 지키도록 테스트 |

## 4. 신규 기능 (기존 기능이 아님)

- 웰컴 메일 (`member-registered`): 이번에 하지 않음
- 마감 알림 외부 메일 (`notification-created` → 내부 Worker): 필수 요구사항을 끝내고 여유 있을 때
- 비밀번호 재설정 메일 (시스템 구성도에 있음, 1차 제외 범위): 이번에 하지 않음

## 5. 팀 결정 (11-02 확정, 이슈 #1)

1. 지역 데이터: user_db 복사본 (F7 없음)
2. 정책 상세 자격 판정: 판정 코드를 policy·recommendation이 같이 씀 (F8 없음)
3. 회원 탈퇴: `member-withdrawn` 이벤트 도입, Saga는 선택
4. 신규 메일: 마감 알림 메일만 여유 있을 때, 웰컴·비밀번호 재설정은 하지 않음
5. 핵심 차별화 기술: Kafka 이벤트 동기화(`policy-updated`, Outbox, 멱등 처리, 재시도·DLT)
